# БытМаркет: рабочие места и сценарии

Статус: предложение до реализации, для проверки на пилоте. Источник исходных фактов - бриф задачи: опт и розница бытовой химии в Астрахани, около 1000 SKU, пользователь предпочитает привычный рабочий интерфейс. Наличие восьми отдельных сотрудников не подтверждено: ниже перечислены функции, которые могут совмещаться. Каналы заказов и точные параметры условий пока неизвестны. Магазин и склад находятся в одном здании; возможен второй склад в городе. Закупки ведёт ООО, магазин работает как ИП. Рабочий предварительный вариант: ООО ведёт закупки и опт, ИП - розницу; товар передаётся ООО -> ИП. Владелец оставил этот вариант для проектирования, оформление и правила передачи необходимо согласовать с бухгалтером до реальных операций. Подтверждено: оптовый минимум в штуках (число не задано), скидки и отсрочка; доставка собственными курьерами или самовывоз. Только курьеры доставляют товар, курьеры и торгпреды принимают наличные. По брифу 1С и кассы сейчас нет; провайдер кассы для обязательного кассового сценария MVP ещё не выбран.

## Принцип рабочего места

После входа сотрудник видит очередь своей работы и одно главное действие. Табличные списки, поиск по названию/артикулу, явные статусы и подписи кнопок важнее декоративных показателей. Разделы показываются по правам. Смена рабочего места при совмещении ролей меняет стартовый экран, но не выдаёт новых разрешений. Общий поиск также соблюдает ограничения данных. Рабочее место задаёт разрешённую организацию; если доступны несколько, выбор явный. Организация видна в заказе, платеже, чеке и передаче наличных. Общий адрес не означает общего владельца товара или денежных средств.

## Карта разделов

| Раздел | Рабочие объекты | Основной переход |
|---|---|---|
| Продажи | Заказы, черновики, запросы скидок, возвраты | Заказ -> клиент, строки, сборка, документы, оплаты, доставка |
| Клиенты | Карточки, контакты, история заказов, согласованные условия | Клиент -> повторить заказ по текущим условиям |
| Товары | SKU, единицы, упаковки, цены, доступность по складам | Товар -> добавить в заказ или посмотреть движение |
| Склад | Остатки, резервы, сборки, приёмки, расхождения | Задание -> фактические количества -> подтверждение |
| Закупки | Предложения пополнения, поставщики, заказы поставщикам | Дефицит -> черновик закупки -> приёмка |
| Деньги | Подтверждённые поступления/возвраты, сверка, задолженность, счета | Счёт/заказ -> сопоставить подтверждённую оплату |
| Доставка | Задания, назначения, статусы, исключения | Готовый заказ -> назначить -> подтвердить результат |
| Отчёты | Продажи, остатки, возвраты, дебиторка, валовая прибыль при достаточных данных | Показатель -> исходные операции с теми же правами |

Настройки пользователей, прав, справочников и аудита доступны отдельным служебным пунктом. Они не занимают место в повседневной навигации продавца.

## Сценарии по ролям

| Роль и стартовый экран | Сценарий и ответственный переход | Минимум обязательных данных | Исключение и критерий приёмки |
|---|---|---|---|
| Владелец: «Обзор», «Требует внимания», «Подробные отчёты» | Просмотреть низкие остатки, запросы скидок/возвратов, расхождения и просрочки; открыть источник; принять решение | Решение, причина отклонения/исключения | Нет данных -> «Данные ещё не внесены», а не нули. Каждое уведомление открывает конкретный SKU/заказ |
| Продавец: «Новая продажа» и свои незавершённые | Сканировать SKU -> количество -> наличная/безналичная/смешанная оплата -> чек/выдача; складское задание только при необходимости | SKU, количество/единица, точка, способ и суммы оплаты; клиент по условиям продажи | Недостаток, изменившаяся цена, запрет скидки не теряют корзину. Нет анонимной оптовой продажи без необходимых данных |
| Менеджер: «Мои заказы» | Создать клиента/заказ -> согласовать условия -> запросить скидку -> передать на склад -> отслеживать оплату и выполнение | Клиент для именного заказа, позиции, склад, ответственный; адрес только при доставке | Чужой клиент не появляется без доступа. Повтор заказа создаёт новый проверяемый черновик |
| Торгпред: «Мой день» на телефоне | План визитов -> клиент/акции -> заказ или результат/причина отказа -> следующая задача; сбор и сдача наличных | Клиент/точка, дата и результат визита; причина отказа; позиции и количество для заказа | Без сети сохраняется только локальный черновик с временем снимка данных. Резерв, цена и принятие заказа подтверждаются после связи |
| Бухгалтер: «К сверке» | Открыть основание -> выписать счёт -> внести/сопоставить подтверждённое поступление -> сверить задолженность | Для платежа сумма, валюта, дата, источник подтверждения, ссылка на основание; для счёта реквизиты продавца/покупателя по выбранному шаблону | Счёт на оплату != кассовый чек != карточка реквизитов. Создание счёта не означает оплату. Повторное подтверждение не удваивает деньги |
| Склад: «К сборке» | Взять задание -> отметить фактическое количество -> заявить расхождение -> передать готовность | Задание, фактические количества; причина расхождения обязательна | Недостача не заменяется скрыто другим SKU. Приёмка возврата не создаёт автоматического возврата денег |
| Диспетчер: «Неназначенные доставки» | Проверить готовность -> назначить курьера/дату -> контролировать исключения | Заказ, адрес и контакт, исполнитель; интервал если согласован | Не назначать заказ без адреса или с незавершённой сборкой без явного разрешённого исключения |
| Курьер: «Мои доставки сегодня» | Открыть задание -> доставить -> при необходимости принять наличные -> отметить результат; отдельно сдать деньги | Задание, результат; причина неудачи; подтверждение вручения по согласованной политике | «Доставлено» не значит «Оплачено». При отсутствии связи результат ожидает синхронизации, серверный статус не подменяется |

Быстрая кассовая продажа, три способа оплаты и чек входят в MVP. Провайдер кассы и порядок подтверждений проверяются до промышленного запуска. Предкодовые UI-прототипы демонстрируют сценарии, не являются разработанной CRM и не создают реальные платежи/чеки.

## Текстовые wireframes

Общий desktop: слева разрешённые разделы; сверху название рабочего места, поиск в доступной области, переключение роли; в центре рабочая очередь; справа контекст выбранной записи. На узком экране контекст открывается отдельной страницей с возвратом к прежнему фильтру. Числа имеют единицу и период. Цвет всегда дублируется текстом.

### Владелец / desktop


Основной экран содержит ровно три вкладки: «Обзор», «Требует внимания», «Подробные отчёты». Вкладка «Обзор» показывает продажи, деньги и остатки с периодом и переходом к исходным операциям. «Требует внимания» содержит низкие остатки, запросы, расхождения и несданные деньги. «Подробные отчёты» раскрывает операции и фильтры.

```text
Обзор | Требует внимания | Подробные отчёты
Период [сегодня]                         Склад [все разрешённые]
Обзор: продажи / подтверждённые деньги / состояние остатков
Требует внимания: товар | склад | доступно / порог [Открыть]
                 запрос | ответственный | срок [Принять решение]
                 сотрудник | несдано | с какого дня [Расшифровка]
Подробные отчёты: фильтры -> показатель -> исходные операции
```

Пустая очередь означает отсутствие задач; ошибка загрузки не отображается как ноль. Без данных показатели имеют пояснение, без себестоимости прибыль не рассчитывается.

### Продавец / desktop и mobile


```text
Новая продажа                     Точка / смена / организация ИП
[Сканировать или найти SKU] -> количество -> корзина
Клиент [по необходимости]         Итого ... [К оплате]
[Наличные] [Безналичные] [Смешанная]
Наличными: получено / сдача; безналично: сумма / подтверждение
[Принять оплату] -> Чек [Ожидает / Выдан / Ошибка] -> [Выдать товар]
```

Передача заказа на склад не обязательна. Минимум: SKU, количество/единица, точка, способ и суммы оплаты. Каждая часть смешанной оплаты имеет собственный статус; сумма частей сверяется с итогом. Ошибка безналичной части сохраняет факт внесённых наличных, повторяется только неуспешная часть. При подтверждённой оплате и ошибке чека предлагается повтор фискализации, не оплата заново. Клиент обязателен только по условиям сделки. Провайдер кассы/эквайринга и процесс подтверждения проверяются до рабочего запуска; кассовые функции не переносятся из MVP на потом.

```text
Мои заказы                  Организация [разрешённая] [Новый заказ]
[Поиск] [Статус] [Ответственный в моей области] [Срок]
Заказ | Клиент | Сумма | Оплата | Выполнение | Следующее действие
```

### Торгпред / mobile


```text
Мой день                     [Дата] [Личный план: факт / цель]
План визитов: время | клиент/точка | задача | статус [Открыть]
Мои задачи: срок | действие [Выполнить / Перенести с причиной]
Акции: условия / срок [Товары]
Визит -> клиент -> [Начать] [Заказ] [Повторить] [Принять наличные]
Результат: заказ / отказ / не состоялся; причина; следующая задача
Мои деньги: собрано / сдано / несдано [Оформить сдачу]
```

Торгпред фиксирует результат визита; отказ и несостоявшийся визит требуют причины. Без заданного личного плана показывается «План не задан». Акции применяются по актуальным условиям, сотрудник не меняет их себе. Торгпред не доставляет товар. При повторе заказа показываются текущие цены и остатки; offline создаётся только локальный черновик без резерва. Эти функции входят в MVP.

### Бухгалтер / desktop

```text
К сверке     Организация [разрешённая]     Счета | Поступления | Возвраты денег | Долги
Основание | Контрагент | Начислено | Подтверждено | Остаток | Статус
Карточка: реквизиты [Просмотреть]  Счёт [Создать документ]
Поступление: сумма, дата, источник/номер подтверждения, основание
[Сохранить черновик] [Подтвердить поступление]
```

Оплата без подтверждения имеет статус «Ожидает проверки» и не уменьшает долг. Дубли источника блокируются. Частичная оплата и переплата показаны отдельно. Связанный кассовый чек показан отдельно от счёта; выдача требует подключения выбранной кассы. Исправления проведённых операций выполняются корректировкой с причиной.

### Склад / desktop или планшет

```text
К сборке                  [Мой склад] [Очередь / В работе / Расхождения]
Заказ | Срок | Позиций | Исполнитель [Взять]
Позиция | Требуется, ед. | Фактически [поле] | [Недостача]
[Сохранить прогресс] [Завершить сборку]
```

Не показывать закупочную цену и прибыль. Нельзя завершить при необработанном расхождении. Конфликт параллельной сборки сообщает, кто уже взял задание. В режиме приёмки тот же принцип, но основание - поставка или возврат; брак поступает в недоступное состояние до решения.

### Диспетчер / desktop

```text

Заказ | Адрес | Контакт | Готовность | Интервал | Курьер [Назначить]
```

Карта и оптимизация маршрута - позднее, только после подтверждения процесса. Переназначение отзывает доступ прежнего курьера и фиксируется в истории. Проблема не исчезает при переносе даты.

### Курьер / mobile

```text
Мои доставки сегодня
Адрес | Интервал | Количество мест | Статус [Открыть]
Задание: адрес, контакт [Позвонить], инструкция, места
[Доставлено] [Не удалось доставить]

```

Нет доступа к общему справочнику клиентов. Повторное нажатие не дублирует событие. Приём наличных курьером и торгпредом входит в MVP; отдельные сбор, сдача и фискальный статус описаны в разделе наличных.

## Сбор и сдача наличных


Сбор: выбрать доступного клиента/основание, сумму, подтвердить факт получения. Сохраняются сотрудник-получатель, время и уникальная операция. До предусмотренного подтверждения получения денег статус «Ожидает проверки», долг не уменьшается. Подтверждённый сбор уменьшает клиентский долг, но не означает сдачу сотрудником. Без сети запись ожидает синхронизации и не меняет серверный долг.

Сдача: сотрудник создаёт передачу с конкретными сборами и суммой; бухгалтер/назначенный принимающий подтверждает фактически принятую сумму. Частичная сдача оставляет остаток; расхождение требует причины. Сотрудник не подтверждает сдачу сам себе. Подтверждённые операции не переписываются, исправление оформляется отдельно.

Минимум полей сбора: организация из основания/разрешённого рабочего места, основание, сумма, сотрудник из сессии, дата, подтверждение по процессу. Сдачи: организация, сдающий, принимающий, связанные сборы, сумма, дата и подтверждение. Деньги разных организаций не объединяются в одну передачу и не погашают чужую дебиторку. Курьер работает с назначенной доставкой, торгпред - с разрешённым клиентом/заказом. Самовывоз не создаёт курьерское задание.

Фискальный статус учитывается отдельно: «Не сформирован», «Ожидает», «Выдан», «Ошибка», ссылка на чек. Сбор, сдача и фискализация не заменяют друг друга. До выбора и настройки кассы реальные операции не включаются в эксплуатацию, но интерфейс и процесс входят в MVP.

Несданные деньги = подтверждённые сборы - подтверждённые сдачи - отдельно подтверждённые допустимые возвраты/корректировки этих сборов. Ожидающие подтверждения суммы показаны отдельно. Отчёт содержит сотрудника, клиента/основание, дату, возраст, остаток и историю. Сдача не создаёт повторную выручку или повторную оплату клиента. Владелец/бухгалтер видят разрешённую общую область, сотрудник только свои суммы.

Приёмка: сбор 1000 и сдача 600 оставляют 400 несданных; повторное подтверждение не удваивает деньги; сбой чека не изменяет факт оплаты; торгпред не получает доставку. Пилот дополнительно измеряет кассовую продажу, визит без заказа и частичную сдачу. До запуска уточняются число штук оптового минимума, размеры скидок, сроки/лимиты отсрочки и провайдер, а не необходимость этих функций.

## Организации, склады и документы

Один адрес магазина и склада не объединяет остатки ООО и ИП. У позиции остатка есть организация-владелец, склад и состояние; резерв проверяет именно их. Продажа ИП не создаёт резерв товара ООО автоматически. До согласования передачи ООО -> ИП нельзя моделировать её простым перемещением между местами хранения или незаметной сменой владельца. В предварительной модели оптовый заказ относится к ООО, розничная продажа - к ИП; рабочее место предлагает соответствующую разрешённую организацию. До реальных операций бухгалтер подтверждает оформление модели и передачи ООО -> ИП.

Заказ, платёж, чек, счёт, реквизиты и передача наличных имеют согласованную организацию. Смена организации в черновике перепроверяет товары, цены, доступность, права, основания оплаты и документы. У подтверждённых операций организация не переписывается без предусмотренной корректировки. Документ и реквизиты для отправки берутся из выбранного юридического лица, с видимыми названием и идентификатором; общий адрес не является ключом выбора. Автоматическая отправка клиентам не разрешена.

Второй склад проектируется как отдельное место хранения с правами и доступностью, но не считается уже действующим. Проверка: при наличии 10 единиц у ООО и нуля у ИП кассовая продажа ИП не может резервировать эти 10 единиц. Передача наличных ИП не принимает сбор ООО. Счёт/чек ИП не формируется с реквизитами ООО. До рабочего запуска владелец с бухгалтером подтверждают оформление предварительной модели ООО: закупки/опт, ИП: розница, процесс и документы передачи ООО -> ИП; отдельно определяется необходимость 1С на старте.

## Низкие остатки

Подтверждённое требование: уведомить владельца при остатке меньше 50 единиц. Предложение для проверки: порог задаётся для каждой комбинации организация-владелец + SKU + склад, по умолчанию 50 базовых единиц SKU; доступно = пригодный физический остаток - активные резервы в пределах организации-владельца товара и склада. Упаковки переводятся по явно заданному коэффициенту. Ожидаемая поставка не увеличивает доступное количество. До запуска владелец выбирает, порог относится к физическому или доступному остатку и всем или отдельным складам.

Событие возникает при переходе из значения >= порога в значение < порога. Дедупликация по организации-владельцу + SKU + складу + эпизоду дефицита: дальнейшее падение обновляет существующую запись, а не отправляет новые одинаковые сообщения. Восстановление до порога закрывает эпизод; новое падение открывает следующий. При первом включении создаётся одна сгруппированная очередь текущих дефицитов. Подтверждение просмотра не скрывает продолжающийся дефицит. Подтверждённый канал уведомлений - только внутри CRM. Внешние сообщения не входят в сценарий. Без достоверных остатков показывать отсутствие данных, не выдумывать дефицит.

## Аналитика и деньги

- Операционный показатель «Заказы» не равен выручке. Период, склад, статус и основание включения всегда видны.
- Продажи после возвратов = сумма признанных продаж после скидок - сумма признанных товарных возвратов по исходной стоимости продажи. Правило признания (например, отгрузка) и учёт налогов утверждаются с бухгалтером; черновики и отмены исключены.
- Себестоимость реализованного = себестоимость отгруженных единиц - восстановленная себестоимость принятых возвратов. Метод оценки запасов требует решения; неизвестную себестоимость нельзя подставлять нулём.
- Валовая прибыль = продажи после возвратов - себестоимость реализованного; валовая маржа = валовая прибыль / продажи после возвратов × 100%, только при положительном знаменателе. Это не чистая прибыль: расходы, налоги и прочие затраты ещё не учтены.
- Денежный поток = подтверждённые поступления - подтверждённые выплаты за период. Возврат товара и возврат денег - связанные, но разные события.
- Задолженность по основанию = признанное требование - зачтённые подтверждённые оплаты - применимые кредитовые корректировки; переплата учитывается отдельно. Нельзя дважды уменьшать долг и товарным возвратом, и тем же возвратом денег.
- На каждом отчёте доступны расшифровка до операций и отметка неполноты данных. Сверка итогов проводится на тестовых частичных оплатах, возвратах разных периодов и отменах.

## Первая версия и последующие этапы

P0: три вкладки владельца; быстрый кассовый сценарий продавца; «Мой день» торгпреда с визитами, задачами, результатами, акциями и личным планом; базовые скидки, отсрочка и оптовый минимум в штуках; роль и область доступа; поиск по ~1000 SKU; заказ/черновик и повтор с перепроверкой; назначенные клиенты; раздельные статусы оплаты и выполнения; задания склада; подтверждение денег; пороговые уведомления; базовые отчёты с расшифровкой; аудит. Доставка своими курьерами и самовывоз входят в P0, как и сбор наличных курьером и торгпредом. Торгпреду в P0 разрешён локальный черновик без резерва, если подтверждена необходимость работы без сети; не полноценная offline CRM.

Для рабочего MVP нужна настройка кассы и оплаты. При необходимости обмена с 1С на старте он включается в P0 после определения конфигурации, данных, направлений обмена и доступа; без этой зависимости его этап согласуется отдельно. Позже: расширенная банковская сверка, сложные оптовые прайсы, маршрутизация, полноценное планирование закупок, расширенная работа без сети. Их внедрение зависит от процесса, доступов и отдельных проверок. Прототип интерфейса не обеспечивает серверные гарантии.

## Пилот и открытые решения

До пилота записать исходное время и ошибки на реальных задачах: найти товар, оформить типовой заказ, повторить с изменившейся ценой, обработать недостачу, сопоставить частичную оплату. На пилоте измерять медиану и верхний квартиль времени, долю завершений без помощи, ошибки количества/цены, число исправлений и обращения за помощью по ролям. Цели улучшения назначаются после исходного замера совместно с владельцем; обещания процентов без данных отсутствуют. Обязательные критерии корректности: ноль двойных заказов от повторной отправки, ноль резервов от offline черновиков, ноль раскрытий чужих клиентов в негативных проверках.

Решения владельца до рабочего запуска: фактический состав команды и совмещение; склады и единицы упаковок; кто и по каким каналам принимает заказ; значения прайсов, скидок, отсрочек и оптового минимума; необходимость клиента в рознице; параметры своей доставки/самовывоза; касса и подтверждение оплаты. Решения бухгалтера: признание продаж, налоги, себестоимость, возвраты, состав документов. Решения команды разработки: серверные транзакции, аудит, защита offline данных и восстановление после сбоя. Эти вопросы не мешают подготовке текстового прототипа, но блокируют соответствующие реальные операции.
