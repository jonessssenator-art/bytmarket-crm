# Источники данных и интеграции БытМаркет

Статус: предложения для выбора, 5 ноября 2026. 1С, касса, банк и оборудование не выбраны. Уведомления подтверждены только внутри CRM, без внешних каналов. Доступы и совместимость API не подтверждены. Ни одна строка ниже не означает работающий обмен. Частоты - проектные предложения, окончательные значения зависят от выбранных систем и возможностей API.

## Общие правила

Одна сущность или явно выделенная группа её полей имеет один главный источник. Реплика и отчётная проекция не становятся вторым ledger. Команда из интерфейса направляется владельцу данных; только его подтверждение означает проведение. Внешние ключи, версии, idempotency key, outbox/inbox, аудит и сверка обязательны. Конфликт не разрешается правилом «последняя запись победила» для остатков, денег и проведённых документов.

Локальный черновик не даёт права продавать по устаревшему остатку. Статус обмена отделён от статуса хозяйственной операции. При неопределённом результате запросить состояние по внешнему ключу до повтора. Экран показывает источник и время актуальности данных. Ручной разбор расхождений оставляет документированный след.

## Вариант А: без 1С

Предложение: БытМаркет ведёт весь оперативный учёт. Банк/эквайер подтверждает движение денег на своей стороне, касса - фискальный результат, но они не изменяют склад напрямую.

| Сущность | Главный источник | Разрешённое редактирование | Направление / частота | Конфликт / нет связи |
|---|---|---|---|---|
| SKU, варианты, упаковки, штрихкоды | БытМаркет | Уполномоченные роли, новая версия упаковки вместо изменения истории | Веб/будущее приложение -> API по команде | Версионный конфликт требует обновления; черновик не меняет каталог |
| Цены и простые акции | БытМаркет | Пользователь с отдельным правом; периоды и версии правил | API -> клиенты при открытии и подтверждении заказа | Сервер пересчитывает и сообщает изменения; офлайн цена справочная |
| Клиент и коммерческие контакты | БытМаркет | Менеджер/торгпред в пределах scope; чувствительные поля отдельно | По команде, проверка версии | Предотвращение дублей, ручное объединение с историей; офлайн только черновик |
| Заказ и строки | БытМаркет | Черновик и разрешённые команды перехода; снимки после проведения неизменяемы | По команде в транзакции | Повтор идемпотентен; без API нет подтверждённого заказа |
| Приёмка, партии, сроки, остатки, резервы, карантин | Ledger БытМаркет | Только документами через складские команды | В одной транзакции; проекции после commit | Блокировки последней единицы; при недоступности сервера проведение остановлено |
| Платёж и распределение по заказам | БытМаркет для оперативного учёта и allocations; банк для факта исполнения внешней операции | Подтверждение адаптером или уполномоченным лицом для поддерживаемого способа; корректировка отдельной операцией | Webhook при наличии + плановая сверка; предложение каждые 15 минут и ежедневно за период | Неизвестный платёж не гасит долг; спорный факт вынесен на сверку |
| Возврат товара и денег | БытМаркет для документов; провайдер для исполнения денежного возврата | Отдельные команды, лимиты исходной продажи/платежа | Товар в транзакции; возврат провайдеру через outbox | Карантин по умолчанию, деньги не считаются возвращёнными до подтверждения |
| Задания доставки и назначение | БытМаркет | Диспетчер назначает, курьер меняет допустимые состояния только своих заданий | По команде; обновление при открытии/возобновлении экрана | Версия предотвращает изменение уже переназначенного задания; офлайн действие ожидает отправки |
| Документы и отчёты | Проведённые записи БытМаркет | Только новая версия/корректирующий документ; отчёты не редактируются | Формирование по запросу, проекции после событий | Указана дата актуальности; расхождение ведёт к первичному документу |

## Вариант Б: 1С:Управление торговлей как главный источник

Предложение требует проверки выбранной версии/конфигурации УТ и способа обмена. БытМаркет становится CRM и интерфейсом команд, УТ ведёт оперативные торговые документы, остатки и резервы. Локальные таблицы склада БытМаркет служат только читаемой проекцией УТ. Локальное проведение отдельного складского ledger отключено. Конкурентность последней единицы и атомарность резерва должны обеспечиваться внутри главного источника; периодическая выгрузка остатков этого не гарантирует.

| Сущность | Главный источник | Разрешённое редактирование | Направление / частота | Конфликт / нет связи |
|---|---|---|---|---|
| SKU, упаковки, штрихкоды | УТ | В УТ; в БытМаркет только запрос изменения, если реализован согласованный API | УТ -> БытМаркет по событию либо предложение раз в 5 минут + ночная сверка | Версия УТ приоритетна; неизвестная упаковка блокирует проведение, история сохраняется |
| Цены и торговые акции | УТ | В УТ; команда из CRM допускается только через подтверждённый контракт | УТ -> CRM при изменении/опросе; обязательный расчёт при подтверждении | Акция в интерфейсе не действует без реализации в главном расчёте; нет связи - только черновик |
| Контрагент, договор, учётные реквизиты | УТ | Команда создания/изменения из CRM либо оператор УТ; подтверждённая запись имеет ID УТ | CRM -> УТ по команде; УТ -> CRM подтверждение/изменения | Идемпотентное создание, сверка дублей; заказ ждёт подтверждённого контрагента |
| Заметки CRM, коммуникации, назначенный торгпред | БытМаркет | В CRM по scope | Локально по команде; обмен только если отдельно требуется | Эти поля не перезаписываются из УТ; конфликт версии решается явно |
| Черновик заказа | БытМаркет | В CRM до передачи | CRM -> УТ по команде подтверждения | Нет связи - «ожидает отправки», наличие и цена не обещаны |
| Подтверждённый заказ, суммы и статусы отгрузки | УТ | Команды изменения/отмены направляются в УТ; факт только после ответа/сверки | УТ -> CRM по событию либо опрос; подтверждение команды проверяется адресно | Внешний ключ предотвращает дубли; локальная кнопка не считается подтверждением |
| Остатки, партии, сроки, резервы, карантин, складские возвраты | УТ | Только проведение в УТ, включая команды из CRM | УТ -> читаемая проекция; резервирование синхронной командой с подтверждением УТ | Недоступна УТ - резерв/отгрузка остановлены. Если конфигурация не поддерживает инвариант, это блокирует вариант до доработки |
| Платежи, allocations, денежные возвраты и задолженность | УТ как оперативный регистр; банк как подтверждение внешнего исполнения | Проведение и распределение только в УТ; CRM отправляет команды | Банк -> выбранный единственный адаптер -> УТ -> CRM; webhook/опрос + сверка | Не вести второй баланс долга в CRM; неподтверждённый результат остаётся в ожидании |
| Назначение курьера и ход доставки | БытМаркет | Диспетчер и назначенный курьер по правам | CRM -> УТ событие доставки при согласованной необходимости; УТ -> CRM факт отгрузки | Доставка не проводит автоматически продажу/оплату; очередь переносит временный сбой |
| Первичные торговые документы | УТ | В УТ; CRM запрашивает представление/печатную форму и хранит ссылку/версию | УТ -> CRM по событию/запросу | Нельзя независимо выпускать расходящиеся первичные документы; недоступная форма помечена |
| Оперативные отчёты | УТ и её читаемая проекция в CRM | Расчёты по подтверждённым версиям, без ручного исправления итогов | Обновление с обменом, полная сверка по расписанию | Показаны задержка и источник; итоги раскрываются в ID документов УТ |

Переключение А -> Б - отдельная миграция: остановка команд записи, сверка каталога/единиц, остатков/партий/резервов, платежей и долгов, перенос внешних ключей и истории, пробное восстановление, контроль итогов, затем переключение владельца команд. Двойная рабочая запись на время «синхронизации» не допускается. Исторические документы сохраняют источник и происхождение.

## Что проверить до выбора

Ответственный за внедрение фиксирует продукт и версию, официальный контракт API, доступную тестовую среду, аутентификацию, события/опрос, лимиты, уникальные ключи, проверку неизвестного результата и порядок восстановления. Для УТ отдельно доказывается атомарный резерв последней единицы, поддержка партий/годности/карантина и корректное распределение денег. Для каждой сущности владелец утверждает строку матрицы; неподдерживаемая функция обозначается ограничением, а не имитируется вторым учётом в CRM.

## Наличные курьеров и торговых представителей

Подтверждено: оба вида сотрудников принимают наличные. Только курьеры доставляют товар; самовывоз является отдельным способом получения. Приём денег и доставка имеют разные права и команды. Минимум оптового заказа задаётся в штуках, число требует ответа; отсрочка и скидки входят в расчёт заказа.

| Сущность | Главный источник А / Б | Разрешённое редактирование | Направление / частота | Конфликт / нет связи |
|---|---|---|---|---|
| CashCollection и подтверждённый платёж | БытМаркет / УТ | Курьер и торгпред инициируют приём в scope; подтверждение создаёт платёж и allocation один раз | А: одна транзакция CRM. Б: команда CRM -> УТ, результат УТ -> CRM | До подтверждения главного источника нет погашения. Неизвестный результат сверяется по ключу; офлайн подтверждение без выбранного решения не заявляется |
| EmployeeCashCustody, наличные сотрудника | Ledger БытМаркет / согласованный регистр УТ | Документы приёма, передачи, возврата и корректировки; прямое изменение баланса запрещено | Вместе с подтверждённым приёмом; в Б читаемая проекция УТ | В Б поддержку регистра требуется доказать или доработать УТ до запуска; второй кассовый ledger в CRM не создаётся |
| CashHandover сотрудник -> касса | БытМаркет / УТ | Сотрудник инициирует, получатель подтверждает фактическую сумму | По команде с идемпотентным результатом | Внутреннее перемещение, не новый Payment/revenue/Allocation. Неподтверждённая сдача не обнуляет остаток сотрудника |
| Сверка и недостача | БытМаркет / УТ | Ответственный сверяет; корректировка отдельным документом | При сдаче и завершении смены/дня по согласованному регламенту | Видны ожидаемая/фактическая сумма, несданные деньги и shortfall; долг клиента не восстанавливается из-за недостачи |
| Фискальный результат наличного расчёта | Выбранная касса, ссылка в главном источнике | Подтверждение адаптера отдельно от подтверждения приёма денег | Согласованный кассовый вызов и проверка результата | Ошибка ККТ не вызывает повторного приёма или погашения. Оборудование и допустимый процесс у клиента выбираются до эксплуатации |

Отчёт о деньгах сотрудников раскрывает сумму до клиентского платежа и внутренних передач. Для УТ проверяется, что подтверждение наличного расчёта и регистр хранения согласованы атомарно либо надёжным подтверждаемым процессом без двойного погашения. Неудачный обмен не скрывается ручным изменением отчётной суммы.

## ООО, ИП и физические склады

Подтверждено: магазин и склад в одном здании, возможен второй склад в городе; закупки компании от ООО, магазин от ИП. Предварительно принят вариант: ООО закупает и продаёт оптом, ИП продаёт в розницу, ООО передаёт товар ИП. Юридическое, договорное и налоговое оформление передачи требует бухгалтера и блокирует соответствующее реальное проведение.

В обеих матрицах `legal_entity_id` является обязательной частью учётной идентичности документа, товарного и денежного владельца. `warehouse_id/location_id` обозначают физическое размещение независимо от владельца. Внешний ID сопоставляется вместе с системой-источником и организацией; одинаковый номер документа двух организаций не означает дубль. БытМаркет в варианте А и УТ в варианте Б должны хранить остатки/резервы раздельно по владельцу даже в одном здании.

| Сущность | Главный источник А / Б | Редактирование и обмен | Конфликт / блокировка |
|---|---|---|---|
| Продавец заказа, организация прайса/кассы/счёта | БытМаркет / УТ | По подтверждённым реквизитам и политике продаж; документы и команды содержат entity | Предварительная маршрутизация: ООО для опта, ИП для розницы; до подтверждения реквизитов и учётной политики рабочее проведение блокируется. Касса/счёт чужого субъекта не подставляются |
| Владелец остатка и резерва | Ledger БытМаркет / УТ | Ключ entity + warehouse + SKU + batch + state; проекция сохраняет этот ключ | ИП не резервирует товар ООО; общий адрес и доступ сотрудника к двум организациям не обходят запрет |
| Передача ООО -> ИП | БытМаркет / УТ по согласованным бухгалтером основаниям | Связанные документы обеих сторон после выбора схемы, с отдельными внешними ID | Не кодировать как обычное перемещение между складами; неизвестные основания блокируют операцию |
| Платёж и распределение | БытМаркет / УТ, факт исполнения у выбранного провайдера | Получатель, счёт/касса и allocations scoped одной организацией | Нельзя погасить долг ИП платежом ООО; ошибочное сопоставление уходит на разбор |
| Наличные сотрудника и сдача | БытМаркет / УТ | EmployeeCashCustody и CashHandover отдельно по организации и её кассе | Общий физический пакет не разрешает взаимозачёт; межорганизационный перевод требует самостоятельного основания |

Кассовый адаптер выбирает конфигурацию по продавцу, банковский - по получателю, Бухгалтерия получает документы соответствующей организации. Проверка включает отказ при несовпадении субъекта, а не только совпадение суммы/номера. При выборе УТ подтверждается поддержка нескольких организаций и владельцев на одном физическом складе выбранной конфигурацией; неподдерживаемая возможность блокирует вариант до решения, а не компенсируется вторым ledger в CRM.

До утверждения схемы ООО -> ИП доступны раздельные отчёты выручки и прибыли. Консолидация требует связанных межорганизационных документов и утверждённого исключения внутренней реализации, стоимости и нереализованной внутренней наценки запасов; простой суммой выручки/GP двух субъектов её не заменять. Ключ эпизода низкого остатка предлагается как организация + SKU + склад, с подтверждённым порогом 50; эта гранулярность ещё требует решения владельца.
